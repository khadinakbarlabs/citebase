# Citebase competitive product audit
19 November 2026 · Internal product planning

## What to build first

Give every recommended fix a permanent place in the project. A customer should be able to open the exact page or answer that triggered a recommendation, choose who will handle it, and come back after the next check to see what changed. Build this once for the dashboard and the AI assistant. It gives customers a reason to return and a reason to buy another check when the result will inform a decision.

Citebase already has many of the expensive pieces: saved projects, repeated AI questions, rival comparisons, a site crawler, search positions, outreach guidelines, and scheduled checks. The strongest opportunities are in the handoffs between those pieces. Two dashboard shortcuts can also give customers the wrong impression about what has been connected or imported.

The public Actor’s latest tag returned **0.5.13**. The sample project renders controls and fictional results. A separate private QA record documents one managed scheduled run that imported one answer on private build 0.5.3, and a local comparable-loss alert test. That private test and the public dashboard demo establish different things. Treat the signed-in private server smoke and promotion of the candidate as separate release work. ## One example of the finished experience

A payroll company selects “Get more demo requests” and confirms that it serves UK businesses with 10–50 employees. Its assistant and dashboard both show the same priority page. An imported Search Console report shows impressions for a switching-payroll query. The saved AI answers show which engines recommended rivals and whether those answers supplied sources.

1. **Explain the opportunity.** “People looking to switch payroll providers are finding this page. It doesn’t explain how long a switch takes.” Show the actual query, page passage, date and sample size. Ask the customer to confirm the missing fact.
2. **Help someone finish the work.** Offer suggested wording with the verified migration timeline, assign it to the page owner, and record the approved version. A recheck can verify that the text is on the page. Search traffic, demo requests and AI recommendations remain separate observations.
3. **Offer the relevant follow-on.** If a trade publication repeatedly appears in those answers, show the specific article and why its audience could use the company's migration checklist. The next action is “Review this editor pitch.” If the page or editorial fit cannot be established, drop the suggestion.
4. **Make recurrence a choice.** “Check these five questions again next month?” Show the engines and allow site-only checks, fewer questions, cost details on request, or a one-off reminder. The user can pause in either interface.

For a local clinic, use “appointment page,” “treatment questions” and “local directories.” For a shop, use “product page,” “availability” and “buying guides.” Store this vocabulary in the project brief. Use plain labels such as **Sites AI quoted**, **Fix this page**, **Ask the editor**, and **Check again**. During a first small AI check, label the result an early reading and offer a larger sample only if it would change the decision.

## Proposed developer handoff

The current OpenAPI surface lists `/`, `/run` and `/mcp`. Keep existing tools and saved projects working. The contracts below are proposed operations. Implement the shared business logic once, expose it through the existing authenticated transport and MCP first, and add named HTTP routes where an external integration needs them. [Existing OpenAPI schema](../.actor/web_server_openapi.json)

| Proposed operation | Required behavior |
|---|---|
| `GET/PATCH /v1/projects/{id}/brief` | Read or revise the agreed goal, market, language, key pages and editorial rules. Return the revision. Confirm inferred facts separately. |
| `GET /v1/projects/{id}/opportunities` | Filter by page, question, channel or date. Return source, observed date, coverage, suggested action and free/manual alternative. Reading saved findings starts zero provider jobs. |
| `POST /v1/projects/{id}/actions` and `PATCH …/actions/{actionId}` | Create once from a finding, preserve its ID through edits, and record owner, approval version, outcome and recheck. Preserve old to-dos during migration. Detect concurrent edits. |
| `POST …/schedule-plans`, `POST …/schedules`, `PATCH …/schedules/{scheduleId}` | Preview without enabling, explicitly confirm, then offer pause/resume and changes. Bind confirmation to the exact plan, enforce the allowance and deduplicate retries. Account for any Apify platform usage separately from capped data charges. |
| `GET …/runs/{runId}` and `GET …/changes?since=…` | Distinguish queued, running, partially covered, complete, awaiting import and failed. Include timestamps and project attribution. Return a safe summary and a permission-checked evidence link. |
| `POST …/prospects` and `POST …/outreach-drafts` | Save the exact source and intended recipient type. Deduplicate within the business's outreach scope. Track approval, opt-out, reply and verified placement. Keep outreach delivery independent from monitoring. |

For every operation, derive access from the signed-in account and project, use stable run and request IDs, and keep private answer wording and recipient details out of shared reports. Replaying a paid confirmation must return the original receipt. A dashboard refresh must never consume a check. Start with a single user managing several sites before promising team roles or cross-account assignment.

## Revenue without pressure

| Trigger observed in the project | Relevant offer | Customer control and business measure |
|---|---|---|
| First fix completed on a valuable page | Recheck that page or its buyer questions once | Offer the smallest useful check and a saved-data/manual alternative. Measure repeat purchase after a completed fix. |
| The same buyer questions matter every month | Optional recurring monitoring for just that group | Show number of checks, engines, cadence, allowance, stop date and “Show estimated cost.” Paid AI is off until chosen. Measure repeat useful runs, pauses and unexpected-charge complaints. |
| Multiple answers cite the same relevant publisher | Optional contact research for one vetted article | Show the reader fit and manual contact path first. Exclude opted-out recipients. Measure approved drafts, replies and verified mentions separately. |
| An agency already maintains several active projects | Portfolio summary and branded client reporting | Recommend once after multi-client use. Keep single-project reporting available. Measure time saved and repeat reports opened by intended recipients. |

Suppress dismissed offers until the triggering evidence changes. Skip offers on failures, weak evidence and low coverage. Never sell a guaranteed ranking, citation or link. Qualify sponsored links appropriately and keep outreach focused on editorial value. [Google Search spam policies](https://developers.google.com/search/docs/essentials/spam-policies)

For each offer, calculate contribution from actual owner receipts less provider spend, owner-paid compute, failed/retried work and variable delivery costs. Track customer-billed platform usage separately. Current contribution, willingness to pay and conversion lift were not measured here. Instrument them before changing prices or encouraging higher-frequency runs.

## Delivery order and definition of done

| Order | Ship | Evidence required to call it successful |
|---|---|---|
| 1 · Make a recommendation finishable | Project-specific setup/import status, editable brief, permanent action IDs, evidence links and one page recheck. | A second client cannot mark the first client's onboarding complete. An edited action survives a fresh chat and dashboard reload. Track time to first verified fix and share of new projects reaching one. |
| 2 · Make repeat work trustworthy | Common dashboard/agent schedule preview and management, project allowance, per-run import status, opt-in digest. | Create in chat, see in dashboard, pause there, confirm in chat. Retry a confirmation and a scheduled occurrence. Verify one job, correct project, correct import and correct accounting. Track useful scheduled runs and customer-reported unwanted runs. |
| 3 · Expand channels from evidence | Page diff and technical ticket, publisher/customer workflows, shared suppression, correct outcome reporting. | Test an on-page fix, a declined pitch, an opt-out, a genuine reply and a published link. Verify each advances only the correct record. Track completed fixes, reply quality and verified placements. |
| 4 · Test expansion | Try one context-specific offer after a verified win. Start with monthly rechecks or an agency summary. | Compare with a holdout on 30-day verified fixes per active project and contribution per active project. Also monitor dismissals, refunds, pauses and support contacts. Set thresholds after collecting a baseline. |

Launch priority is the first complete journey. A customer who can see the evidence, make a change, and verify it gives Citebase a measurable advantage to test. The audit does not establish overall superiority over competitors.
